## Findings

1. **Two Bridges and two properties**, not one of each. `bridge-lab` + `darderdoor` (DBX2) live in property "lab-oce"; the reported test setup (Bridge, Doorlock, bedlock switch + keypad) is `bridge` + property "oc-bbx". **Needs user confirmation that `bridge-lab`/`darderdoor` are also test devices before any job touches them.**
2. **Relationships are reported on the Bridge and keypad records, not on the lock.** Lock/switch records have `linkedDevices: []`. To find the Bridge for a lock, scan the Bridges' `linkedDevices`. (Answers T3, T8.)
3. **Built-in keypad is not a separate device** (T2): the IGB4 door lock appears once; its keypad has no record.
4. **The linked keypad is `EK2X`** — a prefix **not in the supported-devices table** (docs list EK1X only). The API lists it in `support-pins`, so it is algoPIN-capable per the API. It is linked to the **switch**, i.e. it is the bedlock keypad (answers T3/T5).
5. **The switch (`SW1X`) is typed `Lock` by the API**, has battery and `lockStatus`, and is linked to a Bridge. It is **not** algoPIN-capable (absent from `support-pins`, matches docs). Whether Bridge jobs work on it is still unknown (NF) — not tested.
6. **`lockStatus` exists on the igloohome API** for Bridge-linked lock-type devices (Stoplight rule confirmed; U3).
7. **Bridges have no property (`homeId` absent) and no battery.** Their `lastSync` equals their `pairedAt` → `lastSync` is **not a Bridge health signal** (HYP; confirm with E6).
8. **Internal `id` is not unique:** the IGB4 door lock and the EK2X keypad return the same 13-character `id`. Use `deviceId` as the key everywhere.
9. **Activity history is blocked (403) despite the scope** (U18). Gateway-level denial (plain-text `Forbidden`, same as the missing-scope case). Possibilities: different scope name, endpoint not enabled for TRIAL tier, or not enabled for this client. **Question for igloohome support.**
10. **Trial ends 2026-10-17** (22 days after this run). After that, calls return `402` until a subscription is active.
